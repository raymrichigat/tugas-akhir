## 6. POC LLM Verb Extraction — Validasi & Findings

**Konteks:** Bu Diana 2026-05-16 minta "lempar Sirah ke LLM untuk extract kata kerja → kandidat event". Sudah saya eksekusi POC + validasi 10 sample.

### Setup POC
- Sample N=10 chunks: 5 phase coverage (P0/P5/P8/P11/P14) + 5 Perang Badr depth
- Single-prompt batch chat (gratis, reproducible)
- Output: 18 EVENT candidate + 28 SVO triplet

### Manual validation 10 sample

| Verdict | Count | % |
|---|---:|---:|
| ✅ VALID | 5 | 50% |
| ⚠️ PARTIAL VALID | 4 | 40% |
| ❌ WRONG | 1 | 10% |
| **Effective valid (with simple post-process)** | **9/10** | **90%** |

### 5 Findings utama

1. **Micro-events** yang NER tidak bisa cover — contoh: insiden Abu Lahab vs Abu Rafi' di Zamzam (event tanpa proper noun).
2. **Pattern false-positive:**
   - Parallel construction inference ("Hamzah dan Ali" → simetris paksa)
   - Inferred verb (verb tidak literal di kalimat)
   - Schema force-fit unary→binary (Najasyi memeluk Islam dipaksa jadi triplet ke Muhammad)
3. **Semantic predicate enrichment** — beyond INVOLVED_IN generik:
   - `MEMBUNUH` (Hamzah → Utbah)
   - `MEMUKUL` (Abu Lahab → Abu Rafi')
   - `MENGUTUS` (Nabi → Amr → Najasyi)
   - `BERTUJUAN_KE` (Isra' → Baitul Maqdis)
4. **Confirmation Amr Bin Umayyah real prominent** sebagai diplomat, bukan generic sahabat.
5. **Estimasi scale-up full corpus:** 1094 chunks × ~1.8 candidates/chunk = ~1970 EVENT candidate (40× current). Cost API ~$45 + 5-10 jam manual review.

### Output file
`data/result/llm_verb_extraction/manual_validation_10samples.md`

### Yang harus disampaikan

> "Bu, POC LLM verb extraction sudah saya eksekusi sesuai instruksi Ibu. Validated 90% effective di 10 sample. Yang menarik, LLM **bisa identify event yang NER tidak bisa** — contoh insiden Abu Lahab vs Abu Rafi' di Zamzam, event historis tanpa proper noun, NER tidak nangkap. Untuk TA ini saya posisikan sebagai **future work scale-up**, karena untuk full corpus butuh API ~$45 dan manual review 5-10 jam."

### Q13: Schema KG ada relasi apa saja? (kalau Bu Diana lupa)

> **Jawaban:** "Bu, ada **7 jenis relasi** + 1 dari Cypher import:
> 1. INVOLVED_IN (PERSON→EVENT) — 273 edges, weight 0.2-1.0 by frequency
> 2. KELUARGA (PERSON→PERSON) — 110 edges, weight 0.55, 5 subtype (anak/pasangan/saudara/orangtua/paman-bibi)
> 3. OCCURRED_AT (EVENT→LOCATION) — 81 edges, weight 0.2-1.0
> 4. OCCURRED_ON (EVENT→TIME) — 54 edges, weight ~0.5
> 5. SAHABAT (PERSON→PERSON) — 38 edges, weight 0.55, subtype 'sekutu'
> 6. MUSUH (PERSON→PERSON) — 17 edges, weight 0.55
> 7. PRECEDES (EVENT→EVENT) — 15 edges, weight bervariasi (chronology)
> 8. IN_PERIOD (EVENT→Period) — 65 edges, generated saat Cypher import (no explicit weight)
>
> **Weight schema:**
> - Person-Person structural relations (KELUARGA/SAHABAT/MUSUH) = fixed 0.55
> - INVOLVED_IN/OCCURRED_AT/OCCURRED_ON = weighted by frequency (0.2-1.0)
> - Distribusi: 38% edges weight=0.55 (relasi struktural), 30% weight=0.5 (frequency 1), 16% weight 0.2-0.4 (low evidence), 6% weight=1.0 (high-confidence)."

### Q13b: Bagaimana cara hitung weight INVOLVED_IN?

> **Jawaban:** "Bu, weight INVOLVED_IN/OCCURRED_AT/OCCURRED_ON dihitung dari **frequency ko-okurensi** Person/Location/Time dengan Event di chunk yang sama. Logic:
> - frequency=1 → weight=0.5 (default)
> - frequency=2 → weight=0.55
> - frequency=3+ → weight scale up sampai cap 1.0
>
> Edge yang ke-extract dari multiple chunks (frequency >1) lebih kuat sinyalnya. Untuk relasi struktural (KELUARGA/SAHABAT/MUSUH) saya pakai fixed 0.55 karena ekstraksi pattern-based — sekali match sudah valid."

### Q14: Kenapa tidak pakai POS-tag?

> **Jawaban:** "Bu, karena BERT-based NER **tidak butuh POS-tag eksplisit**. IndoBERT pre-trained sudah secara implisit belajar morfo-sintaktik (termasuk POS) lewat attention mechanism. Adding POS-tag manual di setup transformer adalah pendekatan klasik CRF/HMM era pre-2018 (Lafferty 2001). Modern NER (Devlin 2019, Wilie 2020) tidak pakai. Penambahan POS biasanya marginal gain atau malah hurt performance. Untuk SRL-NER kita, label semantik (PERSON/LOCATION/EVENT/TIME) sudah encode role-like information via BIO tagging."

### Q15: SCL vs JSCL — kenapa SCL menang?

> **Jawaban:** "Bu, di S2:
> - SCL (Khosla 2020) = strict supervised contrastive — anchor & positive harus same class
> - JSCL (Dewabharata) = Jaccard similarity contrastive — measure overlap tag set, lebih lenient
>
> Di data Sirah, SCL (F1=0.9215) > JSCL (0.8915). Hipotesis: data kita class-imbalanced parah (PERSON dominant), strict SCL lebih helps karena enforce sharp class boundary. JSCL yang lenient cenderung blur boundary di data minoritas. Tapi ini specific ke characteristic dataset — bukan klaim general."

### Q16: λ_C kenapa 0.3?

> **Jawaban:** "Bu, di S3.1 saya sweep λ_C ∈ {0.1, 0.2, 0.3}:
> - λ=0.1: 0.9477 (di bawah S1)
> - λ=0.2: 0.9470 (di bawah S1)
> - **λ=0.3: 0.9522 (di atas S1)** ← winner
>
> Insight: bobot contrastive loss perlu cukup besar (0.3) untuk dominate cross-entropy yang sudah saturate di kelas mayoritas. Bobot kecil (0.1-0.2) tidak cukup push representasi kelas minor."
